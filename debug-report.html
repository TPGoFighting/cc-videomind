3D 模型渲染 Bug 分析报告

VideoMind — glb-decoration.tsx · 2026-05-26

1. 故障现象

首页共放置 5 个 GLB 3D 模型（Parrot / Stork / Flamingo / SittingBox / Horse），用于装饰页面。模型均能正常加载和解析，但实际渲染结果：

模型文件大小渲染状态
Parrot.glb97 KB不可见
Stork.glb77 KB不可见
Flamingo.glb77 KB不可见
SittingBox.glb422 KB正常
Horse.glb182 KB不可见

特征：只有 SittingBox 能正常渲染，其余 4 个模型完全不可见（仅能看到 Canvas 背景色）。在调试中强制替换为高亮绿色 MeshBasicMaterial 后问题依旧，证明并非材质/光照问题。

2. 调试过程

阶段 1：怀疑加载失败

检查 Network 面板，所有 .glb 文件均返回 HTTP 200，加载成功。排除网络问题。

阶段 2：怀疑材质/光照

MeshStandardMaterial（PBR）在无环境贴图时颜色偏暗。尝试转换为 MeshPhongMaterial，加强灯光强度，问题依旧。排除光照问题。

阶段 3：激进调试 — 高亮 BasicMaterial

将所有材质强制替换为亮绿色 MeshBasicMaterial("#00ff88")（完全不受光照影响），并设置 Canvas 背景为暗紫色以提供对比。结果：SittingBox 变绿可见，其余 4 个依然不可见。

结论：问题不在材质或光照，而在模型的空间位置。 模型 geometry 虽然加载成功，但被放置在了相机视锥之外。

阶段 4：包围盒数据诊断（定位根因）

4. 根因分析

4.1 错误的代码逻辑

// useFrame 中的首帧居中逻辑（修复前）
if (baselineY.current === 0 && groupRef.current.children.length > 0) {
  // Step A: 在 scale=1 时计算包围盒
  const box = new THREE.Box3().setFromObject(groupRef.current);
  const center = box.getCenter(new THREE.Vector3());
  //   → center.y = 83 (Parrot 未缩放的几何中心)

  // Step B: 用未缩放的 center 设置 position
  groupRef.current.position.set(-center.x, -center.y, -center.z);
  //   → position.y = -83 ❌

  // Step C: 然后才设置缩放
  groupRef.current.scale.setScalar(scaleRef.current);
  //   → scale = 0.013
}

4.2 数学分析

Three.js 中节点的世界变换矩阵为：

Mworld = T(position) · R(rotation) · S(scale)

即 先缩放，再旋转，最后平移。对于模型上的一个顶点 v，其世界坐标为：

vworld = position + rotation · (scale × v)

以 Parrot 为例（首帧旋转为 0）：

vworld = (-83) + 0.013 × v
模型中心 v = 83 时：vworld = -83 + 0.013 × 83 = -81.9

模型世界坐标中心在 y = −81.9，而相机位于 z = 3.5，fov = 40°。相机在 y 轴方向的可视范围约为 ±2.5 单位，模型远在 82 单位之外。

4.3 为什么 SittingBox 正常？

SittingBox 的 maxDim ≈ 2.02，缩放因子 s ≈ 1.089（接近 1）。

center ≈ (0, 0, 0)（模型本身接近原点）
vworld = 0 + 1.089 × 0 = 0 → 完美居中

缩放因子越接近 1，位置误差越小。Parrot/Horse 等模型的缩放因子极小（0.013~0.003），导致 position 设定的偏移量相对于缩放后的模型尺寸被放大了 77~333 倍。

4.4 量化误差公式

实际偏移 = centerbox × (1 − scale)
≈ centerbox（当 scale ≪ 1 时）

对于大尺寸模型，centerbox 可达数十到数百单位，误差也因此达到数十到数百单位，远远超出相机视锥范围。

5. 修复方案

核心思路：先缩放，再计算包围盒，再居中

保证居中偏移量基于已缩放的坐标系，与模型最终渲染尺寸一致。

5.1 修复后的代码

// useFrame 中的首帧居中逻辑（修复后）
if (baselineY.current === 0 && groupRef.current.children.length > 0) {
    const s = scaleRef.current;
    groupRef.current.scale.setScalar(s);        // ① 先缩放
    groupRef.current.updateWorldMatrix(true, true);  // ② 刷新世界矩阵
    const box = new THREE.Box3().setFromObject(groupRef.current);  // ③ 再算包围盒
    const center = box.getCenter(new THREE.Vector3());
    groupRef.current.position.set(-center.x, -center.y, -center.z); // ④ 居中
    baselineY.current = groupRef.current.position.y;
}

5.2 修复效果验证

以 Parrot 为例，修复后：
scale = 0.013（先应用）→ box 包围盒在缩放后空间计算
centerscaled ≈ (0, 1.08, 0)
position = (-0, -1.08, -0)
vworld = -1.08 + 0.013 × 83 = 0 → 模型居中在原点

6. 总结

项目内容
Bug 类型3D 空间位置计算错误（坐标系不一致）
直接影响4 个 GLB 模型被放置在相机视锥外（偏移 50~300+ 单位）
根本原因居中偏移量用未缩放坐标系计算，但 Three.js 的 TRS 变换顺序是 Scale → Rotation → Translation，导致大尺寸模型偏移被等比放大
修复方法先 setScalar(scale) → updateWorldMatrix() → 再 Box3().setFromObject() → 最后 position.set(-center)
受影响文件components/glb-decoration.tsx（useFrame 首帧居中逻辑，4 行改动）
为何 SittingBox 正常其原生尺寸 ≈ 2 单位，缩放因子 ≈ 1.09，误差可忽略
调试教训BasicMaterial 绿色覆盖是验证"材质 vs 位置"问题的有效手段；包围盒日志是定位空间问题的关键数据！！！！！！关键发现！ 堆栈显示 page.tsx 是 Server Component，而 GLB_MODELS 来自 "use client" 的 glb-decoration.tsx。RSC 客户端边界序列化导致新键值为 undefined——Turbopack 生成的服务端代理模块是旧版本，不含后来添加的键。 解决：把 GLB_MODELS 提取到独立文件（纯数据，不需要 "use client"）。
