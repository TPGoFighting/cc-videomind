时间线错误原因
第一次部署 400 Bad Request response_format: { type: "json_object" } 不被 DeepSeek 兼容的 API 支持
第二次部署（400 回退后） Zod 验证失败 回退请求返回了自然语言文本，贪心正则提取到的 JSON 缺少 summary、takeaways 等必填字段
根因：用户的 AI Provider（DeepSeek 兼容）不支持 OpenAI 的 response_format 参数，而取掉该参数后，模型在没有明确 JSON 示例的情况下，倾向于返回自然语言解释 + 松散 JSON，导致后续 Zod schema 校验失败。

🧱 三层防御架构

修复不是单点打补丁，而是在 Prompt → 提取 → 验证 三个环节各加一层防御：

层级 环节 改动 文件
L1 Prompt 层 — 嵌入 JSON Schema 示例 在 prompt 中用 JSON.stringify(schemaExample) 展示精确的目标结构，明确禁止 markdown 和额外文本 prompts.ts
L2 提取层 — 括号计数法 + 修复 用逐字符括号计数替换贪心正则 /\{[\s\S]*\}/；解析失败后尝试修复尾部逗号、单引号 provider.ts
L3 验证层 — 结构化修复回退 Zod 校验失败时，从已有字段提取 + 字幕自动生成默认值，兜底保证返回合法结构 provider.ts

L1   Prompt 层：嵌入 JSON Schema 示例

改动前

// 只有英文自然语言指令，模型容易"自由发挥"
"Return strict JSON with: summary, takeaways, suggestedQuestions, highlights."

改动后

const schemaExample = {
  summary: "一句话概述视频内容",
  takeaways: ["关键点 1", "关键点 2", "关键点 3"],
  suggestedQuestions: ["问题 1", "问题 2", "问题 3"],
  highlights: [{ startTime: 10.5, endTime: 35.2, title: "亮点标题", quote: "原文引用", reason: "为什么重要" }]
};

// Prompt 内容：
"你必须返回如下 JSON 结构（不要添加任何解释、markdown 标记或额外文本）：
{
  \"summary\": \"一句话概述视频内容\",
  \"takeaways\": [\"关键点 1\", \"关键点 2\", \"关键点 3\"],
  ...
}"

原理：大语言模型在 prompt 中看到具体 JSON 示例后，会以极高的概率复刻该结构。这比 "Return strict JSON" 的自然语言指令有效得多，本质上是利用了模型的 pattern-matching 能力。同时用中文重写指令，与模型返回中文内容的预期保持一致。

L2   提取层：括号计数法 + JSON 修复

改动前：贪心正则

// 问题：无法正确处理嵌套对象和字符串内的花括号
const match = content.match(/\{[\s\S]*\}/);
// 输入: "答案是 {\"key\": \"value {nested}\"}" → 可能截断在字符串内的 {

改动后：逐字符括号计数

function extractBalancedJson(text: string): string | null {
  const start = text.indexOf("{");
  if (start === -1) return null;
  let depth = 0, inString = false, escape = false;
  for (let i = start; i < text.length; i++) {
    // 正确处理：转义符 \、字符串边界 "、嵌套深度
    if (escape) { escape = false; continue; }
    if (char === "\\" && inString) { escape = true; continue; }
    if (char === '"') { inString = !inString; continue; }
    if (inString) continue;
    if (char === "{") depth++;
    else if (char === "}") { depth--; if (depth === 0) return text.slice(start, i + 1); }
  }
  return null;
}

原理：维护三个状态变量 — 嵌套深度 depth、是否在字符串内 inString、是否遇到转义符 escape。只有不在字符串内时才对花括号计数，depth 归零时即为匹配的闭合位置。这是手写 JSON 提取器的标准做法。

提取出的 JSON 如果仍然解析失败（尾部逗号、单引号等），还会过一道 repairBrokenJson() 做语法修复。

L3   验证层：结构化修复回退

这是最后的兜底线。如果前两层都过了（JSON 提取成功），但内容不符合 Schema（比如模型漏了 highlights 字段），不会直接报错，而是启动修复流程：

function repairAnalysis(value, transcript, zodError): VideoAnalysis {
  // 1. 从解析值中尽力提取已有字段（支持多种 key 命名）
  const summary    = getString(value, ["summary", "description", "overview"]);
  const takeaways  = getStringArray(value, ["takeaways", "keyPoints", "key_points"]);
  const highlights = getHighlights(value);

  // 2. 缺失字段从字幕自动生成默认值
  const repaired = VideoAnalysisSchema.safeParse({
    summary:    summary || 字幕前3句拼接,
    takeaways:  takeaways.length≥3 ? takeaways : 头/中/尾三段字幕摘要,
    highlights: highlights.length≥5 ? highlights : 均匀采样6个时间点,
    ...
  });

  if (repaired.success) return repaired.data;  // 修复成功
  throw zodError;                               // 实在不行才报错
}
缺失字段兜底策略
summary取字幕前 3 段拼接，前缀 "关于...的视频分析"
takeaways取头 10 段、中间 10 段、尾 10 段字幕分别拼接，各截 200 字
suggestedQuestions生成 3 个通用问题（"视频主要内容？"、"关键观点？"、"结论？"）
highlights将字幕均匀分成 6 段，每段取起始位置的片段作为亮点
设计考量：这些默认值质量不如 AI 生成的内容，但能保证用户至少能看到一个可用的分析结果，而不是一个错误页面。对于付费产品来说，降级服务远好于服务中断。

1. Prompt 含 Schema 示例 → 发送到 AI
↓
2. 带 response_format → 400 → 回退不带
↓
3. AI 返回文本 → 括号计数提取 JSON
↓
4. JSON 解析失败? → repairBrokenJson 修复
↓

↓

💡 关键设计决策

  • 不试图修复 400 错误本身。用户的 API 不支持 response_format 是服务端能力问题，客户端无法改变。与其纠结，不如让系统在没有该参数的情况下也能正常工作。
  • 括号计数而非正则。贪心正则 /\{[\s\S]*\}/ 有两个致命缺陷：遇到 {"a":"}"} 这样的字符串内花括号会提前截断；遇到嵌套对象可能无法正确匹配。逐字符状态机是处理结构化文本的"正解"。
  • 降级而非报错。L3 的默认值生成看似"粗糙"，但它保证了用户体验的连续性。用户看到的是一个自动生成的分析页面，而不是一个红色的错误提示。
  • 三层独立，互相不依赖。每一层都可以独立生效。即使 Prompt 没有改进（L1 失效），L2 + L3 仍然能兜底。即使提取器失败（L2 失效），如果内容恰好能被直接 JSON.parse，L1 的结果照样能用。
