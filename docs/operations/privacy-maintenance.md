# 隐私维护与账号删除运行手册

本手册用于生产启用账号删除 worker 和数据保留清理。它不替代所在地法律、财务或隐私合规评审。

## 启用前检查

1. 创建并验证 PostgreSQL 可恢复备份，记录备份时间和恢复负责人。
2. 在预发布环境完成 schema 初始化，确认以下表及索引存在：
   - `user_privacy_preferences`
   - `product_events`
   - `account_deletion_requests`
   - `admin_audit_events`
3. 生成两个不同的高熵密钥并放入部署平台的机密存储：
   - `ACCOUNT_DELETION_WORKER_SECRET`
   - `ASYNC_TASK_WORKER_SECRET`
4. 确认应用实例已读取新配置，但不要在日志、工单或聊天中输出密钥值。
5. 使用专用测试账号验证导出和删除申请，不要使用真实客户账号做首次演练。

## 每日维护调用

由受控调度器每天调用一次：

```http
POST /api/internal/account-deletions
Authorization: Bearer <ACCOUNT_DELETION_WORKER_SECRET>
```

维护任务会：

- 处理已超过七天冷静期的待删除申请；
- 清理过期产品事件；
- 清理过期管理员审计事件；
- 返回处理、跳过和失败数量，不返回用户内容。

不要通过浏览器、公开 webhook 或普通用户会话触发该端点。调度器日志只保留 HTTP 状态、执行时间和聚合计数。

## 监控与告警

- 非 2xx 响应立即告警，但重试前先判断是否为配置错误，避免持续打满限流或数据库。
- 单次失败不应跳过后续每日任务；连续失败时保留待处理申请，不要直接改写处理时间。
- `failed` 数量大于 0 时，使用删除申请 ID 和服务端关联 ID 排查；不要把邮箱、字幕、笔记或导出内容写入告警。
- 定期检查最老的 `pending` 申请是否已经超过处理时间，避免静默积压。

## 回滚

1. 先停用调度器，保留待处理申请和数据库表。
2. 回滚应用版本或关闭内部端点的调用方；不要删除表、强制完成申请或改写申请时间。
3. 如果任务在处理中断，先从数据库和审计事件确认每个申请的状态，再决定重试或从备份恢复。
4. 发生误删时立即隔离写入、保存日志和备份链路，并按事件响应流程处理；不要用新的空记录覆盖证据。

账号删除包含不可逆步骤。任何生产恢复都必须基于启用前验证过的备份，而不是假设应用层回滚能恢复已删除数据。

## 轮换 worker 密钥

1. 在机密存储生成新值并更新所有应用实例。
2. 更新调度器使用的新值，执行一次受控健康调用。
3. 确认旧值返回 401 后再从机密存储撤销旧值。
4. 在审计记录中只写轮换时间、负责人和配置版本，不记录密钥本身。
